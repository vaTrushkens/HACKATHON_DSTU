# Архитектура решения

## Схема

```
┌──────────────────────────── Источники данных ────────────────────────────┐
│ Выписка банка (CSV кейса) │ 1С:Клиент-банк │ Счета / договоры │ Ручной ввод │
│ Данные банка: кредиты, зарплатный проект (mock) │ Открытые реестры (mock) │
└──────────────┬──────────────────────────────┬────────────────────────────┘
               ▼                              ▼
     ┌─────────────────────┐        ┌────────────────────────┐
     │ ingest              │        │ PlannedEvent           │
     │ парсинг, очистка,   │        │ (счета, договоры,      │
     │ дубли, сверка       │        │  банк, ручные события) │
     │ остатков, пропуски  │        └───────────┬────────────┘
     └──────────┬──────────┘                    │
                ▼                               │
     ┌─────────────────────┐                    │
     │ categorizer         │  правила → контрагент → ML (TF-IDF + LogReg)
     └──────────┬──────────┘                    │
                ▼                               │
   ┌───────────────────────────┐                │
   │ recurring  │ taxes        │  регулярные платежи, налоговый календарь
   └──────┬─────┴──────┬───────┘                │
          ▼            ▼                        ▼
   ┌──────────────────────────────────────────────────────────┐
   │ forecast.engine                                          │
   │  детерминированный слой (события с датой и источником)   │
   │  + стохастический слой (FlowModel: naive / seasonal / HGB)│
   │  + Монте-Карло (1000 траекторий) → p10/p50/p90, P(<порог) │
   └──────────────────────────┬───────────────────────────────┘
                              ▼
   ┌──────────────────────────────────────────────────────────┐
   │ risk: дата, сумма, вероятность, объяснение, рекомендации │
   │ scenarios: «что если» │ planfact: план-факт, просрочки    │
   │ backtest: rolling-origin, сравнение моделей              │
   └──────────────────────────┬───────────────────────────────┘
                              ▼
   Django REST API (JWT) ──► React UI (ECharts)
                       └──► assistant.tools — инструменты для LLM-чат-бота (задел)
```

## Слои кода

| Слой | Где | Зависимости |
|---|---|---|
| **Доменное ядро** | `backend/cashflow_core/` | pandas, numpy, scikit-learn. Без Django — тестируется и запускается отдельно |
| **Хранение и API** | `backend/apps/*` | Django 5, DRF, PostgreSQL. Тонкие обёртки: достают DataFrame из БД, зовут ядро, сохраняют снапшоты |
| **UI** | `frontend/` | React 18, TypeScript, Vite, ECharts |
| **Ассистент** | `backend/apps/assistant/` | Реестр инструментов с JSON-схемами и контекст компании для будущего LLM |

### Ядро `cashflow_core`

| Модуль | Назначение |
|---|---|
| `ingest.py` | CSV кейса и формат `1CClientBankExchange` → единый DataFrame; удаление дублей; сверка `prev + in − out = balance_eod` — расхождение помечается как пропуск выписки |
| `categorizer/rules.py` | ~45 regex-правил по назначению и контрагенту, приоритет сверху вниз |
| `categorizer/ml.py` | TF-IDF (символьные n-граммы) + логистическая регрессия, обучается на размеченных правилами строках с уверенностью ≥ 0.85; переопределяет только слабые правила (< 0.75) при вероятности ≥ 0.6 |
| `categorizer/pipeline.py` | правила → распространение по контрагенту (пустые назначения) → ML; страховка «категория соответствует направлению» |
| `recurring.py` | группировка по (категория, контрагент, подтип), оценка периода/дня/суммы, проекция на горизонт с переносом на рабочий день; задержки оплаты клиентов из «счёт № X от DATE» |
| `taxes.py` | эвристика режима (ОСНО/УСН), ЕНП до 28-го с переносом, сумма — как в том же месяце год назад × рост, иначе медиана + квартальный uplift |
| `contracts.py` | договор → график платежей: предоплата + расчёт, равные платежи, постоплата с отсрочкой, этапы; для клиентов дата сдвигается на типичную задержку оплаты, разброс — из истории |
| `forecast/series.py` | дневные ряды по рабочим дням: variable / fixed / financing |
| `forecast/models.py` | `NaiveMeanModel`, `SeasonalNaiveModel`, `HGBFlowModel` (глобальная модель на 150 компаниях, цель нормирована на уровень компании, признаки: календарь, лаги, профиль дня недели, сезонный индекс, отрасль) |
| `forecast/engine.py` | сборка прогноза, Монте-Карло, квантили, вероятность пробития порога |
| `forecast/scenarios.py` | модификаторы входов: задержка клиента, падение выручки, внеплановый расход, рост постоянных расходов |
| `risk.py` | уровень риска, дата (первый день P ≥ 50 %), дефицит p50/p10, водопад «почему», рекомендации, список предупреждений |
| `planfact.py` | сопоставление ожидаемых событий с фактом (контрагент + сумма ±10 % + окно дат), план-факт по неделям |
| `backtest.py` | rolling-origin с проверкой даты обучения; фактический остаток (опционально без финансирования); MAE, MSE, RMSE, MASE, Accuracy/precision/recall/F1, матрица, Brier score и покрытие |

### Модель данных (PostgreSQL)

- `Company` — компания, настройки (`min_balance`, `as_of_override`), режим налогообложения.
- `Operation` — операции с категорией, уверенностью и источником категории; уникальность `(company, operation_date, operation_id)` допускает повторные номера документов в разные дни.
- `IngestLog` — отчёты о качестве загрузок (дубли, пропуски, пустые ИНН).
- `RecurringPattern` — выявленные регулярные платежи (пользователь может отключить).
- `PlannedEvent` — счета, договоры, ручные события, данные банка; статусы `expected / matched / overdue / cancelled`.
- `Contract` — условия договора; при сохранении разворачивается в `PlannedEvent` (`external_ref = contract:<id>`), при расторжении события отменяются.
- `CounterpartyCheck` — кэш проверок контрагентов по реестрам.
- `ForecastRun` + `ForecastPoint` — снапшоты прогноза для план-факта.
- `BacktestResult` — результаты сравнения моделей.
- `CompanyMembership` — доступ пользователя к компании.

## Прогноз: как считается

1. **Остаток сегодня** — `balance_eod` последнего дня ≤ `as_of`.
2. **События** — проекция паттернов, налоговый календарь и `PlannedEvent`. Документ заменяет одно совпавшее регулярное событие по контрагенту, категории, сумме и дате. Разные документы объединяются только по явно общему `meta.obligation_key` (ключ одного платежа, не всего договора). Неоплаченный просроченный расход переносится на следующий день; доход — на пять дней с вероятностью не выше 50% и разбросом срока. Факт ограничен датой среза.
3. **Стохастический слой** — операционные потоки от `FlowModel` за вычетом исторической доли известных поступлений/списаний. Для короткой истории используется профиль дня недели компаний той же отрасли и того же набора, доступный на дату среза; если таких данных нет — среднее собственной истории с явной пометкой.
4. **Монте-Карло** — для каждой траектории: поток = среднее × бутстрап отношения факт/база (по истории компании) × уровневый лог-нормальный шок на траекторию; события с `probability < 1` разыгрываются по Бернулли, дата смещается нормальным шумом `timing_std_days`.
5. **Финансирование исключено** — займы учредителя, транши кредитов не прогнозируются: их отсутствие и есть разрыв.
6. **Квантили и риск** — p10/p50/p90 по дням, `prob_below = P(остаток < порог)`, `P(разрыв) = P(min остатка за горизонт < порог)`.

## Инкрементальное обновление

Обученные модели сохраняются в `models_store/*.joblib`. Движок хранит в памяти до восьми статистических расчётов: ключ включает отпечаток истории, модель, дату, горизонт, число траекторий и seed. Добавление/изменение планового события и сценарий переиспользуют прогноз потоков и случайные множители; согласование платежей и итоговые остатки обновляются. Новая выписка изменяет отпечаток и пересчитывает статистический слой без переобучения модели. Это частичное инкрементальное обновление, а не сохранение всех промежуточных состояний между перезапусками. Регулярности для исторического прогноза вычисляются на дату среза, без использования поздней истории.

## Граничные случаи

| Ситуация | Поведение |
|---|---|
| История < 60 рабочих дней | `industry_profile` при наличии отраслевых данных в том же наборе, иначе `short_history_mean`; уровень по собственной истории, метка «мало данных» |
| Пропуски в выписке | сверка остатков помечает дни «скачка», отчёт в `IngestLog` и на дашборде |
| Пустой ИНН | ключ контрагента — нормализованное имя |
| Дубли строк | одинаковый ID в тот же день пропускается; конфликт содержимого отклоняется; разные ID сохраняются. Без ID применяется отпечаток и порядковый номер совпадающей строки с предупреждением о неоднозначности пересекающихся файлов |
| Контрагент пропал | паттерн становится неактивным (нет повторов > 1.6 периода) и не проецируется |
| Закрытый счёт / давно нет операций | предупреждение «выписка может быть неполной» |
| Отрицательный остаток (овердрафт) | учитывается как есть; порог настраивается |

## Безопасность

- JWT (`djangorestframework-simplejwt`), доступ только к компаниям, где пользователь — участник (`core/permissions.py`).
- Фильтр логов `core/logging_filters.py` маскирует ИНН, номера счетов, телефоны, e-mail, значения полей `amount/payment_purpose/counterparty_*`, Bearer-токены; SQL-логи отключены.
- Секреты и строка БД — только из переменных окружения.

## Задел под LLM-ассистента

`apps/assistant/tools.py` — реестр инструментов (`get_forecast_summary`, `get_upcoming_payments`, `run_what_if`, `add_planned_event`, `get_category_breakdown`) с JSON-схемами для function calling; `build_context` собирает компактный контекст компании. Бот будет вызывать те же сервисы, что и UI, поэтому цифры в ответах совпадут с экраном. Подключение провайдера — через `LLM_PROVIDER / LLM_MODEL / LLM_API_KEY`, точка входа `AssistantChatView`.
