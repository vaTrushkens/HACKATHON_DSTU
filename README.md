# Сервис прогноза денежного потока для малого бизнеса

Прототип для кейса «Сервис финансового прогнозирования для малого бизнеса» (Банк Центр-инвест, хакатон осень 2026).

По истории операций расчётного счёта сервис:

- категоризирует операции (правила → контрагент → ML);
- находит регулярные платежи и поступления, считает налоговый календарь (ЕНП до 28-го, квартальные авансы);
- учитывает счета, договоры, ручные события и данные банка как ожидаемые события с указанием источника;
- прогнозирует остаток на каждый день (30–180 дней) с коридором неопределённости (Монте-Карло);
- оценивает риск кассового разрыва: **дата, сумма, вероятность**, объясняет «почему» и предлагает действия;
- показывает сценарии «что если», план-факт и качество прогноза (бэктест трёх моделей).

Стек: **Python 3.12+ / Django 5 / DRF / PostgreSQL 16**, **React 18 + TypeScript + Vite + ECharts**, pandas / scikit-learn.

## Быстрый старт

### Вариант A: Docker

```bash

docker compose up -d --build
docker compose exec backend python manage.py import_dataset --path /data
docker compose exec backend python manage.py train_models
docker compose exec backend python manage.py seed_demo_events --company C037 --as-of 2026-07-01
```

UI: http://localhost:5173 · API: http://localhost:8000/api · логин `demo` / `demo12345`.

### Качество прогноза (для слайда «подход и проверка»)

```bash
python manage.py train_models --train-until 2026-04-01        # честное обучение до тестового периода
python manage.py run_backtest --test-start 2026-04-01 --test-end 2026-08-31

```

Результат появится на странице «Качество прогноза» и в `GET /api/backtest/`.

### Честная оценка категоризации (ручная разметка)

```bash
python manage.py evaluate_categorizer --sample ../data/labels/sample_300.csv --labels ../data/labels/labels_300.csv
```

`data/labels/sample_300.csv` — стратифицированная выборка 300 операций (120 «сложных»: слабое правило, пустое назначение, «прочее»; 60 поступлений и 120 списаний случайно), `labels_300.csv` — разметка по смыслу назначения и контрагента. Результат появляется на странице «Качество прогноза».

| Вариант | Accuracy | Macro-F1 | Ошибок из 300 |
|---|---|---|---|
| Только правила | 99.0 % | 0.88 | 3 (пустые назначения → «прочее») |
| Правила + контрагент | 100 % | 1.00 | 0 |
| Правила + контрагент + ML | 100 % | 1.00 | 0 |

Эта проверка нашла два бага, которых метрика «согласие ML с правилами» не видела: хвост «Без налога (НДС)» уводил закупки в «Налоги» (правила 94 % → 99 %), а ML, обученный только на строках с уверенностью ≥ 0.9, не видел закупок по правилу 0.85 и переписывал «оплата по счету № … за метизы» в «Услуги» (пайплайн 91 % → 100 %). Оговорка: датасет синтетический, формулировки назначений шаблонные, разметка одного человека — на реальных выписках точность будет ниже, поэтому в интерфейсе оставлена ручная правка категории.

## Демо-сценарий

Компания **C037** (детский образовательный центр, ИП): летом выручки почти нет, а зарплата, аренда и ЕНП идут по графику. Реальный разрыв в данных — с 28 июля 2026.

1. На «Обзоре» выбрать C037, дата «сегодня» = 01.07.2026 (ставится командой `seed_demo_events`). Сервис показывает предупреждение: вероятность разрыва, дата около 28 июля – 10 августа, нехватка сотни тысяч рублей, водопад «почему» (зарплата 10-го и 25-го, аренда, ЕНП 28-го).
2. Включить «показать, что было на самом деле» — факт ложится в коридор прогноза, разрыв случился.
3. «Календарь платежей» — регулярные платежи из выписки, налоги, счета (источник виден), ручной ввод «клиент обещал заплатить».
4. «Что если» — задержка клиента на 3 недели / падение выручки на 20 % / внеплановый расход: базовый и негативный прогноз на одном графике, дельта даты и суммы разрыва.
5. «План-факт» — сохранённый прогноз против факта по неделям, события «пришло / не пришло в срок».
6. «Качество прогноза» — сравнение наивной, сезонной и бустинговой моделей, precision/recall по разрывам, время упреждения, калибровка.

## Результаты бэктеста (срезы апрель–август 2026, горизонт 30 дней, 4311 прогнозов, 135 компаний)

Модель обучена только на данных до 01.04.2026. Факт сравнивается без «спасательных» вливаний собственника и кредитов — это и есть вопрос «что было бы без экстренных денег».

| Модель | MAE остатка / мес. оборот | MASE (к «остаток не меняется») | Покрытие коридора 10–90 % | Precision / Recall разрывов | F1 | Упреждение |
|---|---|---|---|---|---|---|
| Градиентный бустинг (глобальная) | **8.2 %** | 1.17 | 79 % | 50 % / 79 % | **0.61** | 9.6 дн. |
| Сезонная наивная | 8.3 % | 1.18 | 78 % | 47 % / 82 % | 0.60 | 9.8 дн. |
| Наивная (среднее 28 дн.) | 9.1 % | 1.28 | 72 % | 48 % / 81 % | 0.60 | 9.6 дн. |

Честные выводы: по ошибке остатка модели близки — на 30-дневном горизонте для малого бизнеса трудно обогнать «остаток не меняется» (MASE > 1), зато такой наивный прогноз по определению не предскажет ни одного разрыва. Основная ценность — детерминированный слой (регулярные платежи, налоги, счета) и Монте-Карло: 79 % реальных разрывов сервис видит заранее, в среднем за 10 дней, при 16 % доле разрывов в выборке. Калибровка вероятности: в бине 80–100 % разрыв происходит в 69 % случаев, в бине 0–20 % — в 1.5 %; средние бины (40–80 %) переоценивают риск — сервис скорее перестрахуется, чем промолчит.

Что улучшит качество дальше: квантильная регрессия вместо бутстрапа отношений (коридор 79 % против целевых 80 % — почти в норме, но бины 40–80 % калиброваны хуже), отраслевые модели для IT/маркетплейсов/сельского хозяйства (у них ошибка выше всего), учёт счетов из 1С/ЭДО как детерминированных событий — в бэктесте они недоступны.

## Ассистент (локальная LLM) и Telegram-бот

Чат на сайте (кнопка в правом нижнем углу) и Telegram-бот используют одну локальную модель через **Ollama** — по умолчанию компактная `gemma4:e2b` (Gemma 4, апрель 2026; ~4.6 ГБ на диске, работает на CPU, русский язык). Модель не считает ничего сама: она выбирает инструмент из `apps/assistant/tools.py` (прогноз и риск, ближайшие платежи, «что если», добавить событие, структура расходов, налоговый календарь), а ответ формулирует по его данным, поэтому цифры совпадают с экраном. Вопросы «как пользоваться сайтом» отвечаются по описанию разделов из системного промпта. Если Ollama недоступна, чат отвечает сводкой по правилам и помечает это.

Режим `LLM_MODE=router` (по умолчанию): выбор инструмента — структурированный JSON по схеме без размышлений (~2–3 с), затем ответ по данным (~5–10 с); на Ryzen 7 без GPU вопрос с данными занимает 9–17 с. Компактные модели в нативном function calling ненадёжны — без thinking описывают вызов словами, с thinking тратят 10–25 с на размышления. Режим `LLM_MODE=native` (нативный цикл с thinking) подходит моделям от ~8B (`gemma4:latest`), но в 2–4 раза медленнее. Защита от ошибок маленькой модели: аргументы приводятся к типам схемы, числа, которых нет в вопросе, отбрасываются (горизонт и дни — как на экране), событие в календарь не создаётся без суммы в тексте запроса.

- `docker compose up -d` поднимает сервисы `ollama` (модель скачивается один раз в volume) и `telegram` (бот запускается, если задан `TELEGRAM_BOT_TOKEN`).
- Чтобы использовать Ollama, установленную на хосте (и уже скачанные модели), в `.env`: `LLM_BASE_URL_DOCKER=http://host.docker.internal:11434`. Если `ollama pull` падает с «redirect target not allowed … non-public 198.18.x.x» — это VPN с fake-ip DNS; выключите VPN на время загрузки или скачайте блобы вручную из `registry.ollama.ai` (манифест + слои, content-addressed).
- Подключение Telegram: окно ассистента → «Подключить Telegram» → ссылка `t.me/<бот>?start=<код>`. Код одноразовый, живёт 15 минут, привязывает чат к пользователю и текущей компании.
- Бот: `/forecast`, `/payments [дней]`, `/company`, `/notify` (по каким компаниям слать уведомления), свободные вопросы → та же модель с историей диалога.
- Уведомления (раз в `TELEGRAM_NOTIFY_INTERVAL_MIN`, по умолчанию 30 мин): предупреждения уровня high/medium из оценки риска (кассовый разрыв, короткий запас, просроченная оплата клиента) и дайджест обязательных платежей на ближайшие `TELEGRAM_REMIND_DAYS` дней. Ключ уведомления стабилен для одной и той же ситуации — повторов нет. Разовая отправка: `python manage.py send_notifications [--dry-run]`.
