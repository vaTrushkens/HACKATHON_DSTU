# Сервис прогноза денежного потока для малого бизнеса

Прототип для кейса «Сервис финансового прогнозирования для малого бизнеса» (Банк Центр-инвест, хакатон осень 2026).

По истории операций расчётного счёта сервис:

- категоризирует операции (правила → контрагент → ML);
- находит регулярные платежи и поступления, считает налоговый календарь (ЕНП до 28-го, квартальные авансы);
- учитывает счета, договоры, ручные события и данные банка как ожидаемые события с указанием источника;
- прогнозирует остаток на каждый день (30–180 дней) с коридором неопределённости (Монте-Карло);
- оценивает риск кассового разрыва: **дата, сумма, вероятность**, объясняет «почему» и предлагает действия;
- показывает сценарии «что если», план-факт и качество прогноза (бэктест трёх моделей).

Стек: **Python 3.12+ / Django 5 / DRF / PostgreSQL 16**, **React 18 + TypeScript + Vite + ECharts**, pandas / scikit-learn.

## Быстрый старт

### Вариант A: Docker

```bash
cp .env.example .env            # при необходимости поправьте DATASET_DIR
docker compose up -d --build
docker compose exec backend python manage.py import_dataset --path /data
docker compose exec backend python manage.py train_models
```

UI: http://localhost:5173 · API: http://localhost:8000/api · логин `demo` / `demo12345`.

Новый набор выписок загружается в интерфейсе: «Добавить данные» в шапке принимает CSV одной или нескольких компаний, TXT 1С:Клиент-банк или ZIP с `companies.csv` и `statements/*.csv` (либо `all_operations.csv`). Каждый набор получает свой UUID, ранее загруженные данные не затрагиваются. Необязательная команда `seed_demo_events --company <код> --as-of <дата>` фиксирует дату «сегодня» компании и добавляет примеры плановых событий.

### Проверка качества прогноза

```bash
python manage.py train_models --train-until 2025-06-30 --skip-categorizer                       # модель потоков только на истории до калибровочного окна
python manage.py run_backtest --models hgb --test-start 2025-07-01 --test-end 2026-03-31 --fit-calibration   # калибровка вероятности на периоде ДО теста
python manage.py run_backtest --test-start 2026-04-01 --test-end 2026-08-31                     # честная проверка: калибровка уже применяется
```

Сырая вероятность Монте-Карло завышена (см. таблицу калибровки ниже), поэтому `--fit-calibration` обучает изотоническую регрессию «сырая вероятность → наблюдаемая частота разрыва» и сохраняет её в `models_store/calibration.joblib`. Дальше сервис и бэктест применяют её автоматически, а в интерфейсе вероятность помечается как откалиброванная. Калибровку нужно обучать на срезах до тестового периода: если периоды пересекаются, бэктест пишет предупреждение. `--no-calibration` показывает сырые вероятности.

Результат выбранной компании появится на странице «Качество прогноза» и в `GET /api/backtest/?company_id=<ID>`. В интерфейсе кнопка «Проверить текущие данные» запускает оценку этой компании с автоматическим выбором исторических срезов. Метрики включают MAE и RMSE в рублях, MSE в рублях², Accuracy / Precision / Recall / F1 разрывов, матрицу ошибок, покрытие, Brier score и ошибку по горизонтам 7 / 14 / 30 дней против гипотезы «остаток не изменится». После изменения выписки результат помечается устаревшим.

По умолчанию факт — реальный остаток из выписки. Для отдельного эксперимента без последующего финансирования есть `--actual-mode without_financing`. Эти режимы нельзя смешивать при сравнении результатов. HGB с неизвестной датой обучения, старыми признаками или обучением после начала теста пропускается с объяснением. При прогнозе из прошлого такая модель заменяется сезонной.

Для оценки компании нужны 120 дней истории и 30 дней известного факта; короткая выписка даёт прогноз, но не метрики. Бэктест по конкретному набору или компании из терминала: `run_backtest --dataset <UUID>` или `--company <код>`. Каждый прогноз сопровождается пошаговым журналом (отпечаток данных, отчёт очистки, категории, регулярности, согласование платежей, модель и дата обучения, параметры симуляции, итоговые потоки), его можно скачать как JSON на «Обзоре».

### Диагностическая оценка категоризации (ручная разметка)

```bash
python manage.py evaluate_categorizer --sample ../data/labels/sample_300.csv --labels ../data/labels/labels_300.csv --output categorizer-metrics.json
```

`data/labels/sample_300.csv` — стратифицированная выборка 300 операций (120 «сложных»: слабое правило, пустое назначение, «прочее»; 60 поступлений и 120 списаний случайно), `labels_300.csv` — разметка по смыслу назначения и контрагента. Команда проверяет соответствие ID и содержимого текущей базе, распространяет категории отдельно внутри каждой компании и сохраняет отдельный диагностический отчёт с матрицей ошибок. Выборка уже использовалась для настройки правил: приведённые ниже результаты не являются независимой оценкой нового набора.

| Вариант                   | Accuracy | Macro-F1 | Ошибок из 300                    |
| ------------------------- | -------- | -------- | -------------------------------- |
| Только правила            | 99.0 %   | 0.88     | 3 (пустые назначения → «прочее») |
| Правила + контрагент      | 100 %    | 1.00     | 0                                |
| Правила + контрагент + ML | 100 %    | 1.00     | 0                                |

Эта проверка нашла два бага, которых метрика «согласие ML с правилами» не видела: хвост «Без налога (НДС)» уводил закупки в «Налоги» (правила 94 % → 99 %), а ML, обученный только на строках с уверенностью ≥ 0.9, не видел закупок по правилу 0.85 и переписывал «оплата по счету № … за метизы» в «Услуги» (пайплайн 91 % → 100 %). Оговорка: датасет синтетический, формулировки назначений шаблонные, разметка одного человека — на реальных выписках точность будет ниже, поэтому в интерфейсе оставлена ручная правка категории.

## Результаты: бэктест с калибровкой от 25.10.2026

Протокол без взгляда в будущее: HGB обучена до 30.06.2025 (версия признаков 2); калибровка вероятности обучена на срезах июль 2025 – март 2026 (2 526 прогнозов, Brier 0,154 → 0,029 на окне подгонки); проверка на срезах апрель–август 2026 (`final_calibrated_9m`): 4 311 прогнозов (1 437 на модель), 135 компаний из 150, горизонт 30 дней, 300 траекторий, 722 секунды. У 15 компаний недостаточно истории. Факт — исходный остаток выписки, включая фактическое финансирование. Калибровка применена ко всем трём моделям (обучена по HGB).

| Модель | Медиана MAE / оборот | MAE, ₽ | RMSE, ₽ | Accuracy | Precision | Recall | F1 | Brier | Покрытие 10–90% |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| HGB | 7,14% | 1 522 978 | 4 206 238 | 96,5% | 67,8% | 56,3% | 0,615 | 0,030 | 79,9% |
| Сезонная | 7,45% | 1 579 834 | 4 436 422 | 95,2% | 51,1% | 63,4% | 0,566 | 0,033 | 76,2% |
| Среднее 28 дней | 8,22% | 1 662 652 | 4 593 339 | 94,9% | 48,4% | 63,4% | 0,549 | 0,034 | 72,2% |

Для HGB: MSE = 17 692 435 655 177,86 ₽²; матрица TP 40, FP 19, FN 31, TN 1 347. Медиана MASE = 3,80; отношение MAE к «постоянному остатку» на горизонте 7 / 14 / 30 дней = 0,86 / 0,95 / 1,06. Калибровка на проверочном периоде: в корзине 0–20 % разрыв случался в 2,2 % случаев, в корзине 40–60 % — в 67,8 %.

Доля реальных разрывов — 4,9%, поэтому Accuracy сама по себе не характеризует детектор: постоянный ответ «разрыва нет» дал бы 95,1% Accuracy и нулевой Recall. Для сравнения, та же модель без калибровки на том же периоде: Accuracy 75,6%, Precision 16,2%, Recall 94,4%, F1 0,276. Калибровка показала, что сырая вероятность Монте-Карло за недели до разрыва почти не информативна (сырые 0,9 соответствуют ≈7 % реальных разрывов), поэтому уверенные предупреждения появляются ближе к дате, а роль раннего предупреждения выполняет «ранний сигнал» по худшим 10 % траекторий (дата и сумма в плохом случае). Будущие кредитные/собственнические вливания не прогнозируются, но входят в фактический остаток.

Полный набор тестов — **109 passed**. Сценарий «загрузить отдельный набор выписок → построить прогноз → получить метрики» проверен через API на трёх компаниях под новыми кодами: импорт 4 секунды, прогноз 0,5 секунды, оценка качества 6 секунд на компанию. Это проверка работоспособности, а не независимый датасет для оценки модели.

### Известные ограничения модели

- **Ранние предупреждения менее уверенные.** После калибровки вероятность ≥ 50 % появляется в основном за 1–2 дня до разрыва; за недели вперёд честная вероятность редко превышает 10–20 %. Поэтому карточка риска всегда показывает и «ранний сигнал»: дату и сумму нехватки в неблагоприятном сценарии (худшие 10 % траекторий), даже когда уровень риска низкий.
- **MASE > 1 на 30 днях.** На полном горизонте медианная ошибка остатка не лучше гипотезы «остаток не изменится»: остаток за месяц зависит от решений владельца, которых нет в выписке. На 7 и 14 днях модель точнее (0,86 и 0,95). Таблица «Ошибка по горизонтам» на странице «Качество прогноза» показывает это для любой компании.
- **Режим налогообложения** определяется эвристикой по доле НДС в назначениях и налоговой нагрузке; на реальных выписках точность ниже, чем на синтетике.
- **Финансирование** (кредиты, займы учредителя) намеренно не прогнозируется, поэтому в бэктесте часть «ложных» тревог — это разрывы, которые владелец закрыл вливанием денег.

## Внешние источники данных и интеграции

Страница «Календарь платежей → Источники данных». Всё, что загружено или получено по API, становится ожидаемым событием с видимым источником и сразу учитывается в прогнозе; повторная загрузка того же файла ничего не дублирует.

| Источник | Как подключается | Что попадает в прогноз |
|---|---|---|
| 1С: счета на оплату | файл CommerceML 2 (выгрузка документов) или таблица счетов CSV/XLSX | оплата по счёту к сроку; для клиентов — со сдвигом на его типичную задержку |
| ЭДО (Диадок, СБИС, Такском) | УПД / счёт-фактура в XML-формате ФНС 5.01–5.03 | направление по ИНН: наш ИНН у продавца → нам заплатят |
| Онлайн-касса / ОФД | отчёт по сменам или чекам CSV/XLSX | безналичная выручка → зачисление эквайринга на следующий рабочий день минус комиссия; наличные справочно |
| Открытые реестры | ключ DaData (`findById/party`, ЕГРЮЛ/ЕГРИП) | статус, ликвидация, банкротство → ниже вероятность оплаты по счетам клиента; без ключа — заглушка с тем же контрактом, помечена звёздочкой |
| Банк | адрес и токен API по контракту `BankClient` в `apps/planning/connectors.py` | кредиты, зарплатный проект, неисполненные платёжки; без ключа график восстанавливается из выписки |

Ключи хранятся по компании (`IntegrationConfig`), наружу отдаются только последние 4 символа; общие значения можно задать в `.env`. Разбор форматов — в `cashflow_core/sources/` (без Django), образцы файлов — в `data/samples/`. Синтетические ИНН датасета начинаются с `00`, поэтому в реальных реестрах их нет — DaData честно вернёт «не найден».

API: `POST /api/companies/{id}/import/invoices/` (file, direction=auto|in|out, deferral_days), `POST …/import/ofd/` (file, fee_pct), `PUT/DELETE …/integrations/{bank|dadata}/config/`, `POST …/integrations/` ({source: bank|registry} — синхронизация; {source, action: "test"} — проверка ключей).

## Ассистент (локальная LLM) и Telegram-бот

Чат на сайте (кнопка в правом нижнем углу) и Telegram-бот используют одну локальную модель через **Ollama** — по умолчанию компактная `gemma4:e4b` (Gemma 4, апрель 2026; работает на CPU, русский язык; `LLM_MODEL=gemma4:e2b` для слабых машин). Модель не считает ничего сама: она выбирает инструмент из `apps/assistant/tools.py` (прогноз и риск, ближайшие платежи, «что если», добавить событие, структура расходов, налоговый календарь), а ответ формулирует по его данным, поэтому цифры совпадают с экраном. Вопросы «как пользоваться сайтом» отвечаются по описанию разделов из системного промпта. Если Ollama недоступна, чат отвечает сводкой по правилам и помечает это.

Режим `LLM_MODE=router` (по умолчанию): типовые вопросы (разрыв, платежи, налоги, структура расходов) маршрутизируются по ключевым словам без модели, остальные — структурированным JSON по схеме без размышлений; затем ответ по данным идёт потоком (SSE) в чат. Системный промпт одинаков на всех шагах, чтобы Ollama переиспользовала KV-кэш префикса. Скорость: на встроенной Radeon 780M (Vulkan, `OLLAMA_IGPU_ENABLE=1` в окружении Ollama — по умолчанию Ollama iGPU отключает) промпт 435 ток/с и генерация 35 ток/с против 147 и 21 на CPU; первые слова ответа появляются через 1–3 с. Бот раз в 25 минут прогревает модель, чтобы не ловить холодный старт. Компактные модели в нативном function calling ненадёжны — без thinking описывают вызов словами, с thinking тратят 10–25 с на размышления. Режим `LLM_MODE=native` (нативный цикл с thinking) подходит моделям от ~8B (`gemma4:latest`), но в 2–4 раза медленнее. Защита от ошибок маленькой модели: аргументы приводятся к типам схемы, числа, которых нет в вопросе, отбрасываются (горизонт и дни — как на экране), событие в календарь не создаётся без суммы в тексте запроса.

- `docker compose up -d` поднимает сервисы `ollama` (модель скачивается один раз в volume) и `telegram` (бот запускается, если задан `TELEGRAM_BOT_TOKEN`).
- Чтобы использовать Ollama, установленную на хосте (и уже скачанные модели), в `.env`: `LLM_BASE_URL_DOCKER=http://host.docker.internal:11434`. Если `ollama pull` падает с «redirect target not allowed … non-public 198.18.x.x» — это VPN с fake-ip DNS; выключите VPN на время загрузки или скачайте блобы вручную из `registry.ollama.ai` (манифест + слои, content-addressed).
- Подключение Telegram: окно ассистента → «Подключить Telegram» → ссылка `t.me/<бот>?start=<код>`. Код одноразовый, живёт 15 минут, привязывает чат к пользователю и текущей компании.
- Бот: `/forecast`, `/payments [дней]`, `/notify` (о каких ситуациях сообщать), свободные вопросы → та же модель с историей диалога. Компания у чата фиксируется той, с которой сделана привязка на сайте — сменить её можно только переподключением; выбора компании в боте нет намеренно.
- Уведомления (раз в `TELEGRAM_NOTIFY_INTERVAL_MIN`, по умолчанию 30 мин) по типам, которые пользователь отметил в `/notify`: кассовый разрыв, денег меньше чем на 2 недели, клиент не заплатил в срок, крупный платёж впереди, дайджест обязательных платежей на ближайшие `TELEGRAM_REMIND_DAYS` дней. Ключ уведомления стабилен для одной и той же ситуации — повторов нет. Разовая отправка: `python manage.py send_notifications [--dry-run]`.
- Ассистент отвечает только о финансах компании и работе сервиса: маршрутизатор относит посторонние вопросы («сколько букв в слове», код, погода) к `offtopic`, и чат возвращает фиксированный отказ, не обращаясь к модели.
